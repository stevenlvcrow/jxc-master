**一、整改定位**

本项目应定位为：**适配餐饮业态的集团/门店进销存系统**。

核心不是单纯做“采购、库存、报表页面”，而是打通：

`基础档案 -> 采购计划 -> 采购订单 -> 收货验收 -> 入库上账 -> 库存出入库 -> 菜品成本卡 -> 菜品自动消耗 -> 成本核算 -> 经营报表`

整改目标是形成真实业务闭环：

- 采购有来源、有审核、有到货、有入库、有退货。
- 库存只被审核后的业务单据影响。
- 菜品销售或消耗能按成本卡自动扣减原料。
- 审批流控制关键业务动作，不配置流程不允许绕过。
- 报表来自真实单据和库存流水，不造数据、不兜底。

**二、总体业务主线**

完整主流程建议定义为：

`物品档案/供应商/仓库/菜品档案`
-> `采购申请`
-> `采购申请审核`
-> `采购订单`
-> `采购收货/验收`
-> `采购入库`
-> `库存余额/库存流水`
-> `部门领料/报损/调拨/盘点/菜品消耗出库`
-> `成本核算/供应商对账/库存报表/菜品毛利分析`

其中餐饮特色链路为：

`菜品档案`
-> `菜品成本卡`
-> `菜品关联物品`
-> `销售/日结/手工消耗触发`
-> `自动生成菜品消耗出库`
-> `审批通过后扣库存`
-> `理论成本、实际成本、毛利差异分析`

**三、基础档案整改**

基础档案是后续业务能否跑通的前提。

需要补齐和规范：

- 物品档案：物品编码、名称、规格、类别、库存单位、采购单位、换算率、保质期、存储方式、是否启用。
- 供应商档案：供应商状态、供货范围、结算方式、联系人、默认税率、适用门店。
- 仓库档案：集团仓、门店仓、后厨仓、吧台仓、半成品仓、报损仓等类型。
- 菜品档案：菜品编码、菜品名称、分类、售价、适用门店、是否启用自动消耗。
- 单位换算：采购单位、库存单位、菜品消耗单位必须能换算。
- 安全库存：最低库存、最高库存、安全库存、补货周期、预警阈值。

整改要求：

- 所有下拉使用字典或业务主数据 API。
- 禁止页面内硬编码业务状态、供应商、仓库、物品。
- 已被业务单据引用的档案不能物理删除，只能停用。

**四、采购管理整改**

采购管理应拆成四类核心单据：

1. 采购单申请  
   门店或部门提出采购需求。  
   字段包含：申请日期、申请部门/门店、申请人、期望到货日、物品明细、申请数量、用途、备注。

2. 采购申请审核  
   支持按明细行审核。  
   可调整审核数量、指定供应商、驳回部分明细、记录驳回原因。

3. 采购订单  
   由已审核采购申请生成。  
   支持一个申请生成多个订单，也支持多个申请按供应商合并成订单。

4. 采购收货/采购入库  
   采购收货记录供应商实际送货情况。  
   采购入库负责库存增加，必须审核通过后才影响库存。

建议业务状态：

`草稿 -> 已提交 -> 审批中 -> 已审核 -> 已下单/已收货/已入库 -> 已关闭/已作废`

关键规则：

- 采购订单不能凭空绕过采购申请，除非业务明确允许“直接采购订单”。
- 采购收货必须能关联采购订单。
- 收货数量可以小于订单数量，形成未收货数量。
- 入库数量以验收实收数量为准。
- 采购退货必须关联收货或入库来源。
- 已审核单据不能直接删除，只能反审核、关闭、作废或红冲。

**五、库存管理整改**

库存模块统一按“单据驱动库存”处理。

入库类：

- 采购入库
- 其他入库
- 生产入库
- 客户退货入库
- 盘盈入库
- 调拨入库

出库类：

- 部门领料
- 客户销售出库
- 报损出库
- 采购退货出库
- 菜品消耗出库
- 调拨出库
- 盘亏出库

库存规则：

- 审核通过才生成库存流水。
- 库存流水生成后更新库存余额。
- 反审核必须冲回库存流水。
- 库存不足时禁止出库，不能静默跳过。
- 盘点期间如启用冻结，相关仓库/物品禁止出入库。
- 库存余额、库存流水、业务单据必须能互相追溯。

**六、盘点管理整改**

盘点应支持餐饮高频盘点场景：

流程：

`创建盘点单 -> 选择盘点范围 -> 冻结库存 -> 录入实盘 -> 生成差异 -> 差异审核 -> 自动生成盘盈/盘亏单 -> 调整库存`

关键能力：

- 支持全仓、分类、指定物品盘点。
- 支持多人盘点。
- 支持草稿保存。
- 支持差异原因：自然损耗、加工损耗、录入错误、丢失、过期、变质。
- 审核通过后不能直接改库存，应生成盘盈入库或盘亏出库。

**七、菜品成本卡与自动消耗整改**

这是餐饮进销存区别于普通商贸进销存的重点。

菜品成本卡定义为菜品 BOM：

- 一个菜品对应多个原料物品。
- 每个原料配置用量、单位、换算率、损耗率。
- 成本卡支持版本、生效日期、停用状态。
- 已被出库引用的成本卡版本不能覆盖修改。
- 成本卡支持集团通用和门店独立版本。

菜品关联物品规则：

- 必须指定原料物品。
- 必须能换算到库存单位。
- 必须指定默认扣减仓库或仓库规则。
- 缺少换算率、仓库、物品时禁止启用。

自动菜品消耗出库规则：

- 支持集团级开关、门店级开关、菜品级开关。
- 开启后，销售完成、日结或手工触发时，根据成本卡生成菜品消耗出库单。
- 自动生成的出库单必须保留来源：菜品、销售单/日结单、成本卡版本。
- 库存不足时生成失败记录，不能自动跳过。
- 未配置审批流时不能直接扣库存。
- 审批通过后扣减库存。
- 已扣库存的自动消耗单不能删除，只能红冲或反审核。

新增流程编码建议：

- `DISH_CONSUMPTION_OUTBOUND`：菜品消耗出库流程

**八、审批流整改**

审批流应覆盖所有关键业务：

采购类：

- `PURCHASE_APPLICATION`：采购单申请流程
- `PURCHASE_ORDER`：采购订单流程
- `PURCHASE_RECEIPT`：采购收货单流程
- `PURCHASE_RETURN`：采购退货单流程

库存类：

- `PURCHASE_INBOUND`：采购入库流程
- `PURCHASE_RETURN_OUTBOUND`：采购退货出库流程
- `DEPARTMENT_PICKING`：部门领料流程
- `DAMAGE_OUTBOUND`：报损出库流程
- `STOCK_TRANSFER`：调拨流程
- `INVENTORY_CHECK`：盘点单流程
- `DISH_CONSUMPTION_OUTBOUND`：菜品消耗出库流程

规则：

- 流程发布页必须能看到这些业务流程。
- 未发布流程模板时，提交/审核失败。
- 审批通过同步业务状态。
- 驳回同步业务状态和驳回原因。
- 反审核同步撤销或重置流程状态。
- 不允许无审批流时自动通过。

**九、报表整改**

报表分四层建设。

采购报表：

- 采购申请执行表
- 采购订单跟踪表
- 采购收货差异表
- 供应商供货统计
- 供应商对账表

库存报表：

- 实时库存查询
- 库存出入库明细
- 库存出入库汇总
- 库存预警
- 库存周转率
- 滞销库存
- 报损损耗分析

菜品成本报表：

- 菜品标准成本表
- 菜品实际成本表
- 菜品毛利分析
- 原料理论消耗表
- 原料实际消耗表
- 理论实际差异表
- 成本卡变更影响分析

经营分析报表：

- 门店库存金额
- 门店损耗率
- 供应商采购占比
- 高耗用原料排行
- 菜品毛利排行

**十、前端整改要求**

结合项目现有前端规范：

- 复杂新增、编辑全部使用跳转页面，不使用弹窗承载复杂单据。
- 新增/编辑共用页面，编辑必须查详情回填。
- 列表统一：查询区、工具栏、表格、分页。
- 动态物品明细表必须支持新增行、删除行、物品选择、单位换算、数量校验。
- 下拉全部走字典或业务主数据。
- 所有接口携带 `orgId`。
- 切换集团/门店后清空旧数据并重新加载。
- 菜单、路由、权限必须同步，不能出现菜单可见但页面无路由。
- 按钮权限前端只做展示控制，最终以后端校验为准。

**十一、后端整改要求**

后端需要统一几类能力：

- 单据状态机：控制草稿、提交、审核、驳回、反审核、作废。
- 库存流水服务：统一处理入库、出库、冲回。
- 审批流桥接服务：业务单据和流程实例双向同步。
- 成本卡版本服务：处理菜品 BOM 生效、停用、引用锁定。
- 自动消耗服务：根据菜品销售或日结生成消耗出库。
- 报表查询服务：只读真实业务表和库存流水。
- 权限校验服务：按集团、门店、角色、流程节点校验操作权限。

工程要求：

- 不跳过 Checkstyle。
- 不加 mock 数据冒充业务完成。
- 不用展示文案做业务判断。
- 不用前端兜底生成关键业务结果。
- 关键状态变更必须事务内完成。

**十二、实施优先级**

第一阶段：打通采购审批闭环  
完成采购申请、审核、订单、收货、退货、流程发布、审批同步。

第二阶段：打通库存生效闭环  
统一入库、出库、调拨、盘点审核后生成库存流水和库存余额。

第三阶段：补齐菜品成本卡  
完成菜品关联物品、成本卡版本、默认扣减仓、单位换算、启停规则。

第四阶段：实现菜品自动消耗  
完成自动开关、生成菜品消耗出库、失败记录、审批、扣库存。

第五阶段：完善报表  
先做库存明细和汇总，再做采购跟踪，最后做菜品毛利和理论实际差异。

**十三、验收标准**

业务验收：

- 采购申请到采购入库可完整流转。
- 采购退货能扣库存并关联原入库。
- 所有库存变化都有来源单据。
- 菜品成本卡能生成菜品消耗出库。
- 自动消耗失败原因清晰可查。
- 未配置审批流时不能提交或审核。
- 报表数据能追溯到原始单据和库存流水。

技术验收：

- 前端构建通过。
- 后端编译通过。
- Checkstyle 不跳过。
- 无 mock、无假数据、无硬编码业务下拉。
- 多集团、多门店切换数据隔离正确。
- 菜单、路由、权限一致。
